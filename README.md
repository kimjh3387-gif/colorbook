# 색칠공부 변환기 (Coloring Page Maker)

사진을 올리면 색을 다 빼고 **색칠공부(coloring book) 윤곽선 그림**으로 바꿔주는 정적 웹 도구.
서버가 없다 — 업로드한 이미지는 브라우저 안(Canvas)에서만 처리되고 어디로도 전송되지 않는다.

아이들용 단순한 그림부터 어른용 정교한 컬러링북까지 **단순화 슬라이더 하나로** 커버한다.

## 두 가지 변환 방식
| | AI 윤곽 (기본값) | 기본 |
|---|---|---|
| 원리 | PiDiNet tiny(사람이 그린 윤곽으로 학습된 경량 엣지 모델)를 onnxruntime-web으로 **브라우저 안에서** 실행 | 아래 "동작 방식"의 컬러 그래디언트 파이프라인 |
| 잘하는 것 | 색은 같고 그림자만 다른 경계(팔·주름), JPEG 노이즈 무시 | 세부 조절(단순화·영역별 적응·음영) |
| 해상도 | 긴 변 1024 (8의 배수로 맞춤) | 긴 변 1200 |
| 속도 | WebGPU 첫 실행 ~2.7초(셰이더 컴파일), 이후 0.25초. WASM 폴백 ~1초 | ~0.5초 |
| 서버/키 | 없음. 모델 0.4MB + 런타임(jsDelivr CDN) | 없음 |

AI 모드를 넣은 이유: 피카츄 썸네일에서 가슴 앞 팔의 위쪽 경계는 밝기가 172→188(16단계)로 완만하게 바뀔 뿐
색은 같아서 그래디언트 방식으론 **신호 자체가 없었다**(히스테리시스 하한을 0.5→0.3으로 내려도 픽셀 단위로 동일).
학습된 모델은 "팔과 몸통은 다른 부위"라는 걸 그림자만 보고 안다. 모델 출처·규격은 [models/README.md](models/README.md).

AI 모드 후처리: 확률 맵에 히스테리시스(상한 thr, 하한 thr×0.35) → 테두리 8px 억제(모델이 가장자리에서
가짜 선을 냄) → 30px 미만 얼룩 제거 → **Zhang-Suen 세선화로 1px 뼈대** → `선 굵기`만큼 원형 확장.
하드 임계값 하나만 쓰면 확률이 오르내리는 약한 선(팔 위쪽)이 점선으로 끊긴다.
세선화를 넣은 이유: 모델 선이 원래 ~5px라 굵기 슬라이더가 "더 굵게"밖에 못 했다. 뼈대로 깎고 키우면
0 = 1px 가는 선부터 20 = 유아용 굵은 선까지 기본 모드와 같은 감각이 된다(20이어도 0.36초).
`선 개수` 슬라이더는 thr = 0.85 − 0.7×(s/100)로 매핑(기본 70 → 0.36). 확률이라 사진마다 흔들리지 않아 백분위가 필요 없다.
`영역별 적응`·`음영`은 AI 모드에선 의미가 없어 숨긴다.

**AI 모드의 `단순화 정도` = 모델에 넣는 해상도.** 0.5→1024, 3(기본)→768, 6.5→512, 12.5→256 (6단계마다 절반).
작은 그림을 주면 모델이 작은 주름은 못 보고 큰 윤곽만 잡는다. 결과 PNG는 확률 맵을 1024로 키워 쓰므로 항상 같은 크기.
- 인형 사진: 1024는 봉제선·털 주름을 전부 선으로 잡았고, 768은 얼굴 그대로 두고 몸통 잔선이 줄었다. 10(~340px)이면 눈·팔도 뭉개짐
- 렌더 피카츄: 768이 1024보다 팔 위쪽이 잘 이어졌다(1024는 점선). 대신 코 점·입 모양은 1024가 낫다 — 트레이드오프

**`잔선 정리`(두 모드 공통)** = 가지치기. 1px 뼈대에서 끝점을 N번 깎고, 살아남은 끝점에서만 원래 선을 따라 N번 되살린다.
→ 윤곽에 매달린 길이 N 이하 가지(주름·노이즈·JPEG 링잉)는 사라지고, 긴 열린 획은 원래 길이로 복구된다.
분기점이 하나도 없는 고립 획(입·눈썹)은 "특징"으로 보호(12px 미만은 노이즈로 삭제).
끝점에서 거슬러 걷는 방식은 계단 대각선에서 가짜 분기점을 만나서 이 방식으로 바꿨다.

### 알고리즘의 한계 (인형 사진으로 확인)
남는 봉제선은 **양끝이 윤곽에 붙은 고리**거나 **긴 고립 획**이라 기하학적으로 입·팔과 구분이 안 된다.
멀티스케일 평균(512+768+1024)도 해봤지만 모델이 봉제선을 진짜 선으로 확신해서 그대로다.
여기서부터는 사람이 지우는 게 답 → **지우개 도구**. 원본이 카드 격자처럼 캐릭터당 50px 수준이면 어떤 방법도 안 된다.

### 지우개
결과 카드 오른쪽 🧽 버튼. 켜고 그림 위를 드래그하면 흰색으로 덮는다. 굵기 4~120px, 되돌리기(Ctrl+Z), 전부 취소.
- 자국은 **캔버스 폭 기준 비율 좌표**로 저장(`eraseStrokes`) → 슬라이더를 다시 만져 결과가 새로 그려지거나
  모드 전환으로 캔버스 크기가 1024↔1200으로 바뀌어도 같은 자리에 다시 얹힌다(`paintMask` 끝에서 `applyEraseStrokes`).
  새 이미지를 올리면 비운다. 다운로드·크게 보기는 캔버스를 그대로 읽으므로 지운 상태가 반영된다.
- 캔버스가 `object-fit: contain`이라 엘리먼트 사각형과 실제 그림 영역이 다르다. 화면 좌표를 바꿀 때
  스케일·레터박스 오프셋을 계산해야 한다(`canvasGeometry`) — 안 그러면 세로 사진에서 클릭 위치가 어긋난다.
- 드래그 중엔 마지막 구간만 덧그리고, 되돌리기는 `lastPaint`(마지막 마스크)로 전체를 다시 그린 뒤 남은 자국을 얹는다.

### 아는 함정: 숨겨진 탭에서는 WebGPU가 멈춘다
브라우저 패널이 화면에 안 보이면(`document.hidden`) GPU 작업이 스로틀돼 tiny 모델이 5초 넘게 걸리거나 아예 안 끝난다.
자동 테스트할 때 패널을 꼭 띄워둘 것. 실제 사용자는 탭을 보고 있으니 문제없음.

### 아는 함정: GitHub Pages에선 WASM 멀티스레드가 안 된다
`SharedArrayBuffer`에 필요한 COOP/COEP 헤더를 Pages가 못 붙인다. 그래서 WASM 폴백은 단일 스레드(~1초)이고,
빠른 건 WebGPU 덕분이다. 스레드 수를 올리려고 삽질하지 말 것.

## 동작 방식 (기본 모드)
목표는 "명암을 흑백으로 바꾸기"가 아니라 **이어진 뚜렷한 윤곽선**을 뽑는 것.
밝기 차이에 그냥 임계값을 걸면 점각(speckle)이 흩뿌려지므로 아래 순서로 처리한다.

1. R/G/B 채널 분리 (휘도는 음영 옵션에만 씀)
   - 처음엔 grayscale 하나로 했는데 캐릭터 그림에서 치명적이었다: 흰 배경 위 노랑은 휘도 차이가 ~50뿐이라
     피카츄 얼굴 윤곽이 끊기고, 노랑 위 빨강 볼·분홍 입은 휘도로는 흐릿하다. **색이 바뀌는 곳**을 봐야 한다
2. 채널별로 박스 블러 2회(가우시안 근사)로 잔 텍스처를 스케일 단위로 제거 — `단순화 정도` 슬라이더
   - 정수 반경 두 개를 섞어 **0.5 같은 소수 반경**도 지원 (슬라이더를 촘촘하게 쓰려고)
3. **블러 반경만큼 떨어진 픽셀**끼리 비교해 색 변화(그래디언트)와 방향 계산 (`gradientColor`)
   - 세기 = 세 채널 변화 벡터를 합친 RGB 거리, 방향 = 가장 크게 변한 채널의 것
   - 블러가 경계를 폭 ~2r의 완만한 경사로 펴놓기 때문에, 이웃 1픽셀만 보는 고정 3x3 커널로는 못 잡는다
4. 그래디언트 방향으로 비최대 억제(NMS) → 경사면 전체가 아닌 능선 한 줄만 남김
5. **영역별 적응** — 픽셀마다 자기 주변 동네의 평균 대비로 나눠 상대적 세기로 환산
   - 사진 전체에 기준 하나만 쓰면 대비가 극단적으로 센 부분이 상위권을 독식한다
   - 격자로 자르면 칸 경계에서 선이 끊기므로, 창이 미끄러지는 방식(박스 블러)을 쓴다
   - **하한선 필수**: 평평한 하늘에서 동네 평균이 0에 가까워지면 미세 노이즈가 "이 동네 1등"이
     되어 없는 선이 생긴다. `globalMean * 0.35` 를 바닥으로 깔아 막는다
   - 강도 0이면 수식상 적응 전과 **완전히 동일한 결과**(균일 스케일링이라 백분위·임계가 같이 스케일됨)
6. 히스테리시스 임계 → 강한 선에서 이어지는 약한 선만 살림 (흩어진 점각이 자동 탈락)
   - 임계값은 절대값이 아니라 **그 사진 자신의 분포 상위 n%** 로 잡아 사진마다 결과가 일정하게
   - 지수 곡선(`0.05 * 100^(s/100)`)이라 낮은 쪽이 촘촘함
   - `선 개수` 기본값 70: 컬러로 바꾼 뒤 흰 배경 실루엣이 상위권을 독식해서 50이면 실루엣만 남는다.
     65는 입이 빠지고 70에서 얼굴이 다 들어오며 75부터 JPEG 링잉이 꼬불선으로 나온다(피카츄 실측)
7. 연결 성분 크기로 남은 얼룩 제거 → **원형 커널**로 굵기 확장 → 흰 배경 + 검은 선
   - 정사각 커널은 면적이 9→25→49px로 껑충 뛰어 중간 굵기가 없다. 원형은 완만하게 는다

`음영(그림자)` 은 기본 꺼짐. 켜면 어두운 영역에 연한 회색 플랫톤만 깔린다(해칭 아님).

핵심 로직은 [script.js](script.js) 하나에 다 있음 (외부 라이브러리 없음, 순수 JS + Canvas API).

## 레이아웃
결과물(색칠공부 버전)이 오른쪽 영역 전체를 쓴다. 원본은 이미지를 올리는 순간 **왼쪽 업로드 칸이
썸네일로 바뀌어** 거기 표시된다(썸네일 클릭 = 다른 이미지 선택, 🔍 = 원본 크게 보기).
처음엔 원본/결과를 나란히 두었는데 1920 화면에서 캔버스 한 장이 400px밖에 안 돼서 바꿨다.
캔버스 틀 높이를 `calc(100vh - 270px)` 로 고정하고 `object-fit: contain` 으로 맞춘다 — 작은 원본도 화면 크기로 확대돼 보인다
(`max-width/max-height` 방식은 원본이 작으면 작은 그대로 떠서 화면이 텅 비었음).

## 작은 원본은 자동 확대 (MIN_DIMENSION = 1200)
실제 사용자 원본은 대부분 **이미지 검색 결과를 우클릭 저장한 400~600px 썸네일**이다.
그 크기에서 단순화 3(블러 반경)을 그대로 걸면 귀·얼굴선 같은 요소가 흐림 단계에서 통째로 지워져
윤곽이 거의 안 잡힌다(피카츄 썸네일로 실제 확인). 그래서 긴 변이 1200px 미만이면 처리 전에
`imageSmoothingQuality: 'high'` 로 1200px까지 확대한다 — 슬라이더 감각이 큰 사진과 같아지고
결과 PNG도 인쇄 가능한 크기가 된다. 420px JPEG(q70)로 검증: 블록 노이즈 없이 윤곽 깔끔, 선 비율 1.6%.

## 아는 함정: 흐림이 가는 선을 지운다

`단순화 정도`를 올리면 **가늘고 대비 약한 요소는 흐림 단계에서 통째로 사라진다.**
한 번 사라지면 뒤에서 임계값을 아무리 조절해도 못 되살린다.

실측(해·광배가 있는 테스트 이미지): 단순화 **2~4에서는 해가 잡히고 6에서는 0**.
그래서 기본값을 3으로 잡았다. "해가 안 잡힌다"는 증상이 나오면
임계값(`선 개수`)이 아니라 **`단순화 정도`부터 낮춰볼 것**.

## 아는 함정: 백분위 히스토그램 칸 수

임계값을 "상위 n%"로 구할 때 히스토그램 칸이 적으면, **선을 많이 뽑는 구간에서 슬라이더가 먹통이 된다.**
임계값이 낮은 쪽은 한 칸에 픽셀이 수만 개씩 몰려서, 슬라이더를 움직여도 같은 칸에 머물기 때문.
(실제로 512칸일 때 `선 개수` 100과 105의 결과가 픽셀 단위로 완전히 동일했다.)

→ 칸을 4096개로 늘리고 **마지막 칸 안에서 선형 보간**까지 해야 연속적으로 움직인다.

## 튜닝 기준
검증할 때 "검은 픽셀 비율"과 "연결 성분(덩어리) 분석"을 같이 본다.
- 선 비율 **2~5%** 가 컬러링북으로 보기 좋은 범위 (10%를 넘으면 뭉개진 덩어리)
- 20px 미만 작은 덩어리가 많으면 = 점각이 흩뿌려진 실패 상태
- 큰 덩어리 몇 개 + 점각 0개 = 이어진 윤곽선이 제대로 나온 상태

## 테스트 방법 (브라우저 자동화)
`samples/`(gitignore)에 이미지를 두고 `python -m http.server 8123`로 띄운 뒤, 페이지 콘솔에서
`fetch('/samples/x.jpg')` → `File` → `DataTransfer`로 `#fileInput.files`에 넣고 `change` 이벤트를 쏘면 업로드와 같다.
결과는 `#resultCanvas.toDataURL()`로 꺼낸다. 브라우저가 CSS/JS를 캐시하니 `fetch(url,{cache:'reload'})` 후 새로고침.
